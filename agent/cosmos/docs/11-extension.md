# 11 扩展性

cosmos 的扩展只有两类：**加一个子 agent** 和 **加一种状态**。前者改桌面，后者改面板。两者都不应该改动核心链路。

---

## 1. 新增子 agent

### 1.1 步骤

| 步 | 动作 | 产出 |
| --- | --- | --- |
| 1 | 想清楚能力边界：做什么、不做什么、输入需要哪些必填参数 | 一段 `description` 草稿 |
| 2 | 定义 `params_schema`（JSON Schema object） | 参数契约 |
| 3 | 实现 `async def handle(request, ctx) -> AgentResult` | handler，遵循 [08](08-subagent-contract.md) |
| 4 | 填 `AgentCard`：`id` / `name` / `icon` / `summary` / `description` / `capabilities` / `examples` | 卡片 |
| 5 | 填 `desktop`：`group` / `order` / `pinned` | 桌面位置 |
| 6 | 填 `execution`：超时、并发、排队、是否可重试 | 执行策略 |
| 7 | 填 `permissions`：默认全 `false`，按需开 | 权限 |
| 8 | 在 `data/config/cosmos.yaml` 的 `agent.cosmos.agents[]` 里登记 | 注册条目 |
| 9 | 补测试：成功、参数缺失、取消、超时 | 测试 |
| 10 | 观察日志与桌面呈现：`readable` 文案是否准确 | 验收 |

### 1.2 九条检查清单

- [ ] `id` 唯一、小写蛇形，且不随展示名变化。
- [ ] `summary` ≤ 20 字，写「做什么」；`description` 写清「不做什么」。
- [ ] `params_schema` 的必填项在 handler 里再校验一遍（不信任上游）。
- [ ] handler 是 `async def`，阻塞操作用 `asyncio.to_thread`。
- [ ] `ctx.report()` 的 `progress` 单调不减，`step` 是短语不是句子。
- [ ] 长时间等待外部资源时调 `ctx.heartbeat()`。
- [ ] 取消路径能清理自己申请的资源。
- [ ] 失败返回 `AgentResult.failed/partial` 并带 `code` 与 `retriable`，不抛业务异常。
- [ ] 不读取对话上下文、不尝试给用户发消息、不调用其它 agent。

### 1.3 桌面注册注意

| 注意 | 说明 |
| --- | --- |
| 展示名用她的语言 | `card.name` 是 Aliya 看到的词，别把 `Edit Agent` 这类工程名直接摆上去；`id` 才是工程标识 |
| 分组先声明 | 在 `desktop.groups` 里加 `key` 与 `title`，否则落 `general` 并 WARNING |
| `order` 留空隙 | 用 10、20、30，后续插入不用全量重排 |
| 不靠 `pinned` 抢位置 | 置顶只给真正高频的 agent；位置跳动比「重要的浮上来」更伤 |
| `visible=false` 要慎重 | 它对 Aliya 不可见但仍可被显式调用，容易造成「看不见但会动」的困惑 |
| 图标用 emoji | 无需资源打包；同一分组内避免重复图标 |

### 1.4 反模式

| 反模式 | 问题 | 替代 |
| --- | --- | --- |
| 把一个 tool 直接包装成 agent | 没有独立生命周期，桌面全是碎片 | 合并到相关 agent，作为其内部工具 |
| 一个 agent 做十件事 | 描述无法写清，匹配准确率下降 | 按动作域拆分（读 / 写 / 检索） |
| `description` 写成营销文案 | 模型匹配靠它，空话会降低准确率 | 写场景、输入、边界与不适用情况 |
| 权限「先全开再说」 | 用户状态泄露面扩大 | 默认全关，按需打开并写清用途 |
| 超时给 0 或不设 | 长任务会永久占住并发槽 | 显式给 `timeout_seconds`，并区分任务粒度 |

## 2. 新增用户状态字段

### 2.1 步骤

| 步 | 动作 | 注意 |
| --- | --- | --- |
| 1 | 在 `PresenceFields` 加子模型 | 字段必须可 JSON 序列化 |
| 2 | 加 `Availability` 判定：什么情况下不可用 | 不可用时必须给 `reason`，不填默认值 |
| 3 | 在 `ReadablePresence` 派生规则里加分支 | 按优先级插到正确位置，不要动既有文案 |
| 4 | 定义推送条件与最小间隔 | 抖动大的字段一定要去抖 |
| 5 | 评估隐私：是否属于最小必要 | 不能回答「为什么 Aliya 需要知道」就不加 |
| 6 | 加配置开关 | 与字段一一对应，可单独关闭 |
| 7 | 决定是否进 `WorldInput` | 只进结论性信号，不进整份快照 |
| 8 | 补测试：可用 / 不可用 / 陈旧 / 关闭 | 四种状态都要覆盖 |
| 9 | 更新 [04](04-presence.md) 的字段表与规则表 | 文档是契约 |

### 2.2 硬性要求

| 要求 | 原因 |
| --- | --- |
| 必须有 `unknown` 路径 | 通道能力不一致，缺失是常态 |
| 派生表述必须带不确定性 | 「可能」「通常」而不是断言 |
| 情绪类字段必须带 `confidence` 与 `source` | 无证据的情绪推断是冒犯 |
| 不得引入新的采集通道而不加开关 | 用户必须能关 |
| 不得把字段写进日志 | 泄露面 |
| 不得让子 agent 默认可见 | 默认全拒 |

### 2.3 反例与替代

| 想要 | 问题 | 更好的做法 |
| --- | --- | --- |
| 采集剪贴板判断用户在忙什么 | 严重越界 | 不采集 |
| 用消息长度推断情绪 | 无依据、易误判 | 用 `decision`/`llm` 打分并给置信度 |
| 用回复延迟推断忙碌 | 风格差异被误读 | 只在通道显式上报 `busy` 时使用 |
| 采集地理位置推断作息 | 越界且不必要 | 用 `active_hours` 统计 |

## 3. 新增事件主题

新增主题必须同时改动四处，缺一不可：

1. `CosmosCapabilities.event_topics` 里声明（否则 `handshake` 后 Aliya 不会订阅）。
2. `ControlService.subscribe()` 的主题校验白名单。
3. `CosmosEvent.payload` 的模型定义（放在 `contracts`，可 JSON 序列化）。
4. 本文档与相关章节的事件表。

命名约定：

| 规则 | 示例 |
| --- | --- |
| 小写点分，`域.对象.动作` | `agent.state.changed` |
| 状态变化用 `changed` | `presence.changed` |
| 一次性结果用名词 | `agent.result`、`world.inference` |
| 不用动词开头 | 不写 `notify_user` |

事件的 `sequence` 在同一主题内递增，跨主题不保证有序。消费方必须按 `event_id` 去重。

## 4. 版本与兼容

| 版本 | 位置 | 变更规则 |
| --- | --- | --- |
| `contract_version` | `handshake()` | 主版本不同 → 直接报错；次版本新增字段 → 兼容 |
| `AgentCard.version` | 卡片 | 参数或语义变化时递增；破坏性变更升主版本 |
| `api_version` | `handshake()` | 方法签名变化时升主版本 |

兼容策略：

| 变更 | 是否兼容 | 处理 |
| --- | --- | --- |
| 给模型加可选字段 | 是 | 消费方忽略未知字段 |
| 给 `AgentResult` 加字段 | 是 | 同上 |
| 改字段语义（同名字不同义） | **否** | 新增字段 + 旧字段标记废弃 |
| 删除字段 | **否** | 先标记废弃一个版本，再删 |
| 改 `params_schema` 必填项 | **否** | 升 `AgentCard.version` 主版本 |
| 新增事件主题 | 是 | 旧消费方不订阅即可 |
| 改事件载荷字段 | **否** | 新增主题或升主版本 |

废弃流程：标记 `deprecated` → 文档标注 → 保留至少一个次版本 → 删除。删除前在 `handshake().features` 里去掉对应能力标识。

## 5. 常见坑

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 自然语言总匹配到错的 agent | `description` 太笼统、`examples` 缺失 | 补场景与反例，加 2–3 条典型请求 |
| 进度条不动 | handler 没调 `ctx.report()` | 至少报开始与结束两次 |
| 桌面一直显示「运行中」 | handler 退出但没返回 `AgentResult` | 运行期判 `failed(internal)`；检查异常是否被吞 |
| 任务取消后资源没释放 | handler 吞了 `CancelledError` | 让它继续传播，用 `finally` 清理 |
| Aliya 收到的上下文里混着 `task_id` | 写进了 `ConversationContext` | 只写 `TaskBrief`，内部标识留调度侧 |
| 用户看到「Edit agent 正在…」 | 回传文本没走脱敏 | 用 `label`/`agent_name`，过滤 `id` |
| 展示名是「Edit Agent」 | 直接把工程名当展示名 | `name` 用她的语言（「编辑台」），`id` 留工程名 |
| 回复像客服 | 用了「已为您完成」「正在处理」 | 按人设语气重写：短句、带语气词、说人话 |
| 短句被拼成一段、句号被删 | 通道做了「润色」 | 关闭合并与标点规范化 |
| 状态推送过于频繁 | 没去抖 | 按字段设 `min_interval`，typing 用 settle |
| 情绪判断忽高忽低 | 单条消息即更新 | 增加 `evidence_count`，用滑动窗口 |
| 主动消息在深夜发出 | 免打扰时段没配 | 检查 `quiet_hours` 与用户时区 |
| 世界推理建议与 Aliya 正在做的事冲突 | 没提供 `aliya_context` | 用 `set_aliya_context()` 告知未收尾话题 |
| `get_presence()` 返回空导致崩 | 采集关闭时返回了 `None` | 规范要求返回 `unknown` 快照 |
| 加新字段后老客户端报错 | 消费方按严格 schema 解析 | 契约模型统一 `extra="ignore"` |

## 6. 扩展评审清单

提交前逐条确认：

| 维度 | 问题 |
| --- | --- |
| 边界 | 这个能力是「执行」还是「调度」？放错层会让职责塌陷 |
| 权限 | 是否申请了不需要的权限？能不能默认关？ |
| 隐私 | 新字段能否回答「Aliya 为什么必须知道」？ |
| 对等 | 这个字段如果反过来给她自己看，她会舒服吗？ |
| 人设 | 展示名与文案是不是她的语言？有没有混进「agent / 模型 / 用户 / 调度」？ |
| 信息差 | 有没有越过时间同步原理、装置、Doll 身份这些禁区？ |
| 语气 | 会不会破坏她的短句节奏、标点、无旁白规则？ |
| 可解读 | 新状态有没有给人类可读的结论，而不只是数值？ |
| 降级 | 拿不到数据时是否显式 `unknown`，而不是默认值？ |
| 幂等 | 重复调用是否安全？副作用能否承受重放？ |
| 取消 | 长任务能否在 5s 内退出？资源是否清理？ |
| 观测 | 失败时日志里有 `agent_id` / `task_id` / `错误类型` 吗？（不含正文） |
| 文档 | 契约变了，字段表与事件表同步更新了吗？ |
| 测试 | 成功、失败、取消、超时、未知状态五条路径都覆盖了吗？ |

---

## 7. 不该扩展的方向

以下需求经常被提，但会破坏既有边界，建议先讨论再动手：

| 需求 | 为什么危险 | 替代 |
| --- | --- | --- |
| 让子 agent 直接给用户发消息 | 绕过 Aliya 与脱敏，人格分裂 | 子 agent 返回 `message`，由 Aliya 转述 |
| 让世界推理触发调度 | 参谋变成指挥官，责任无法归属 | 输出 `action_windows`，由 Aliya 决策 |
| 给 Aliya 开注册权限 | 等于让它给自己造工具、扩权限 | 走部署配置 |
| 让 cosmos 合并多 agent 的结论 | 通道替决策者下判断 | 只汇总状态，内容交 Aliya |
| 用用户状态做画像与推荐 | 越界，且难以撤回 | 只做即时协作所需的判断 |
| 把 agent 桌面暴露给用户 | 内部编排细节外泄 | 用户侧只看到任务与结果 |
